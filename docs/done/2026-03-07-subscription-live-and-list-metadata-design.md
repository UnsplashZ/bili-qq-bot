# 订阅直播与列表元数据修复设计

日期：2026-03-07

范围：

- 设计修复“直播推送有时整场漏推”的订阅直播链路
- 设计修复 WebUI 订阅列表用户头像不显示的问题
- 设计修复 `/订阅列表` 图片中缺少认证标签的问题

非目标：

- 本文不直接修改任何生产代码
- 本文不重构整个订阅系统的数据模型
- 本文不处理直播之外的动态、视频、专栏推送语义

---

## 1. 背景

当前有 3 个明确问题：

1. 直播推送存在“有时整场都不推”的现象。
2. WebUI 订阅列表中的用户头像全部不显示。
3. `/订阅列表` 生成图片中的用户头像没有认证标签。

静态梳理后可确认：

- WebUI 订阅列表走 `src/dashboard/routes/api/modules/subscriptions.js`，用户订阅会经过 `subscriptionUserMetaCacheService.enrichSubscriptions()` 补全展示元数据。
- `/订阅列表` 仍在 `src/commands/subscription.js` 中单独调用 `biliApi.getUserCard()` 构造头像数据，未统一使用元数据补全服务，也未向图片渲染层传递认证信息。
- 直播推送分为手动订阅直播检查和 Cookie 同步直播检查两条路径，但两边都出现“整场漏推”，说明问题更可能出在共享的直播状态确认逻辑、上游直播字段不稳定时的处理策略，或状态推进边界，而不只是某一条分支独有的 bug。

---

## 2. 目标

本次修复后的目标：

1. WebUI 订阅列表中的用户订阅默认显示头像；远程头像失效时回退默认头像。
2. `/订阅列表` 图片中的用户项显示头像，并在有认证信息时显示认证标签。
3. WebUI 与 `/订阅列表` 共享同一套订阅用户展示元数据来源，减少字段漂移。
4. 直播检查在上游接口返回不完整时，不再把“未知状态”误判为“确认未开播”，从而降低整场漏推风险。
5. 直播状态只在“确认状态变更且通知链路允许推进”时落盘。

---

## 3. 方案选项

### 方案 A：最小补丁

做法：

- WebUI 继续使用现有接口，单独排查头像字段为何未展示。
- `/订阅列表` 继续走命令层自己的 `getUserCard()`，仅额外拼接认证字段。
- 直播检查只在现有 `checkUserLive` 上加判空和日志。

优点：

- 改动最小，见效快。

缺点：

- 订阅用户元数据仍然维护两套来源。
- 容易只修表象，不解决字段漂移问题。
- 对直播整场漏推的防护有限。

结论：不推荐。

### 方案 B：统一展示元数据 + 收紧直播状态确认

做法：

- 将订阅用户的 `name / face / officialVerify` 统一收敛到 `subscriptionUserMetaCacheService` 提供。
- WebUI 和 `/订阅列表` 共享同一套补全结果。
- 图片渲染层增加认证徽标渲染。
- 直播检查明确区分“确认开播 / 确认下播 / 状态未知”，对状态未知不推进状态。
- 对主信号不完整的场景，使用直播房间信息做二次确认。

优点：

- 同时覆盖 3 个问题。
- 元数据来源统一，后续维护成本更低。
- 直播链路对上游字段抖动更稳健。

缺点：

- 改动中等，需要补充针对性验证。

结论：推荐。

### 方案 C：统一订阅查询器 + 全量状态机重构

做法：

- 进一步收敛手动订阅、Cookie 同步、命令展示、WebUI 展示和推送状态机。

优点：

- 结构最干净。

缺点：

- 范围显著超出当前问题。
- 回归面过大，不适合本轮修复。

结论：不采用。

---

## 4. 推荐设计

推荐采用方案 B：**统一展示元数据 + 收紧直播状态确认**。

### 4.1 架构边界

拆成两个子问题处理：

1. 订阅用户展示元数据层
   - 唯一职责：为 WebUI 和 `/订阅列表` 提供统一的 `name / face / officialVerify`。
   - 数据来源优先级：订阅对象已有字段 -> 本地元数据缓存 -> 远程补拉刷新缓存。
   - 输出结果：两个入口都不再各自决定头像和认证字段来源。

2. 直播状态确认层
   - 唯一职责：为手动订阅和 Cookie 同步产出可靠的当前直播状态，以及是否允许推进状态。
   - 核心约束：
     - 拿不到直播状态不等于确认下播。
     - 拿不到房间详情不应直接吞掉一次开播。
     - 两条直播路径共享同一套状态确认规则。

### 4.2 数据流设计

#### WebUI 订阅列表

- 保持 `GET /api/groups/:id/subscriptions` 为唯一入口。
- 在接口层对用户订阅统一执行 `subscriptionUserMetaCacheService.enrichSubscriptions()`。
- 返回契约中，用户订阅项应尽可能包含：
  - `uid`
  - `name`
  - `face`
  - `officialVerify`
- 若补全失败：
  - 名称回退为已有订阅名或 `UID_xxx`
  - 头像回退默认头像 URL
  - 认证字段为空

#### `/订阅列表` 图片

- 命令层不再自行并发调用 `biliApi.getUserCard()` 拼装头像数据。
- 改为复用同一个用户元数据补全服务，得到与 WebUI 一致的用户展示数据。
- 图片生成器读取：
  - `u.face`
  - `u.officialVerify`
- 认证标签渲染规则沿用现有前端定义：
  - `type=0` 个人认证
  - `type=1` 机构认证

#### 直播推送

主检查顺序建议统一为：

1. 读取用户信息中的 `live_room.liveStatus` 与 `roomId`。
2. 若 `liveStatus` 可判定为 `0/1`，作为主信号使用。
3. 若 `liveStatus` 缺失，但本地已有 `roomId`，进入“状态未知”，不直接判定为未开播。
4. 对“主信号不完整但存在房间号”的场景，调用直播房间详情接口做二次确认。
5. 仅在“确认开播且通知允许推进”时写入 `lastLiveStatus = 1`。
6. 仅在“确认下播”时写入 `lastLiveStatus = 0`。
7. 若本轮仍无法确认状态，则保持原状态不动，等待下一轮。

### 4.3 组件修改方向

#### `subscriptionUserMetaCacheService`

职责保持不变，但本轮需作为唯一的订阅展示元数据来源：

- 继续负责 `face` 与 `officialVerify` 提取、缓存、回退。
- `/订阅列表` 命令层也应改为通过它补全用户订阅数据。
- 若远程拉取失败，仍返回可渲染的降级结构。

#### `subscriptions` API

- 保持现有接口协议。
- 增加对返回值完整性的确认，确保前端收到的用户订阅项中 `face` 字段可用于展示。

#### `subscriptionList` 图片生成器

- 在用户卡中显示认证徽标。
- 图片 HTML 中头像增加 `onerror` 默认头像回退，避免远程头像链接失效时空白。

#### 直播检查模块

- 手动订阅直播检查与 Cookie 同步直播检查应共享同一套“直播状态确认”辅助逻辑。
- 将“状态获取”和“状态推进”解耦，避免上游字段空缺时误推进到错误状态。

---

## 5. 异常处理

### 5.1 展示元数据补全失败

要求：

- 不阻塞 WebUI 和 `/订阅列表` 的主流程。
- 订阅名保留原值。
- 头像回退默认图。
- 认证字段置空。

### 5.2 图片渲染头像加载失败

要求：

- 图片 HTML 中通过 `onerror` 回退默认头像。
- 不因为单个头像失效导致整张图渲染异常。

### 5.3 直播房间详情获取失败

要求：

- 不把失败视为“确认下播”。
- 记录清晰日志，包括 uid、roomId、来源路径。
- 维持旧 `lastLiveStatus`，等待下轮重试。

### 5.4 通知失败或不允许推进

要求：

- 沿用现有 `decideAdvance()` 语义。
- 仅在允许推进时更新 `lastLiveStatus`。
- 避免因为一次通知失败把开播事件永久跳过。

---

## 6. 测试设计

### 6.1 元数据补全

应覆盖：

1. 订阅对象已有 `face / officialVerify` 时可直接透传。
2. 订阅对象缺字段时，可从缓存或远程接口补齐。
3. 远程接口失败时，返回默认头像和空认证而不是抛出不可恢复错误。

### 6.2 WebUI 订阅列表

应验证：

1. 用户订阅显示头像。
2. 认证用户显示认证徽标。
3. 头像失效时前端回退默认头像。

### 6.3 `/订阅列表` 图片

应验证：

1. 用户卡显示头像。
2. 有认证信息时显示认证徽标。
3. 个人认证与机构认证样式可区分。

### 6.4 直播状态确认

应覆盖：

1. `liveStatus=1` 时正常推送并推进到 `1`。
2. `liveStatus` 缺失但存在缓存 `roomId` 时，不推进到 `0`。
3. 二次确认接口判定开播时，可触发推送。
4. 二次确认接口失败时，保持旧状态。
5. 明确确认下播时，才推进到 `0`。

---

## 7. 风险与取舍

1. `/订阅列表` 从命令层直接查卡片改为复用元数据服务后，首次刷新可能受元数据缓存刷新时间影响，但收益是两端展示一致。
2. 直播二次确认会增加少量 API 调用，但只在主信号缺失时触发，属于可接受的可靠性开销。
3. 本轮不做全量订阅状态机重构，因此仍保留手动订阅与 Cookie 同步的调用入口差异；不过共享确认逻辑后，直播行为应能显著收敛。

---

## 8. 结论

本轮推荐以“统一订阅用户展示元数据”和“直播状态未知不落盘”为核心策略推进：

- WebUI 与 `/订阅列表` 共用一套用户头像和认证数据补全逻辑。
- `/订阅列表` 图片新增认证徽标渲染。
- 直播检查明确区分确认开播、确认下播与状态未知，避免把未知状态写成已处理，降低整场漏推风险。
