# Logs Scroll UX Design

## 背景

当前系统日志页的滚动体验有两个明显问题，代码集中在 `dashboard/src/pages/Logs.jsx` 与 `dashboard/src/pages/logs/scrollBehavior.js`：

- 页面进入后，历史日志加载与实时日志到来会触发自动滚动，用户刚进入页面就可能被强制拉向底部
- 页面只有顶部的“回到底部”入口，长日志场景下缺少就地返回顶部或快速前往底部的交互

现状中的“接近底部”判断为固定像素阈值：

- `scrollTop + clientHeight >= scrollHeight - 48`

这个阈值对不同屏幕密度、字号和日志项高度不稳定，也不符合“按 3 行日志判定”的目标。

## 目标

- 首次进入日志页时不强制自动下滑
- 只有用户当前仍接近底部时，新增日志才继续自动跟随
- 在日志滚动区内提供单个浮动按钮，支持快速回顶部或前往底部
- 保持改动范围最小，不调整后端接口与日志流协议

## 非目标

- 本轮不重构 `useLogsStream` 的历史加载和 WebSocket 数据模型
- 本轮不改动日志筛选、暂停/继续、清空等现有功能语义
- 本轮不移除顶部已有的“回到底部”按钮

## 方案对比

### 方案 A：继续使用固定像素阈值

将 `48px` 调整为更大的固定值，同时新增浮动按钮。

优点：

- 实现最直接
- 改动少

缺点：

- 不满足“按 3 行日志”需求
- 在不同屏幕与字号下体验不一致

### 方案 B：按 3 条日志高度动态判定

通过已渲染日志项的高度动态计算底部缓冲区，只有当用户仍处于距底部约 3 条日志高度以内时才自动跟随。

优点：

- 与需求一致
- 对不同终端更稳定
- 逻辑仍可保持在纯前端视图层

缺点：

- 需要补充少量测量与状态同步逻辑

### 方案 C：使用底部哨兵 + IntersectionObserver

用底部哨兵元素的可见性决定是否跟随，再补额外缓冲范围。

优点：

- “是否看到底部”语义清晰

缺点：

- 对这个页面偏重
- 仍需额外处理“3 行缓冲区”，收益有限

## 推荐方案

采用方案 B。

这次只在日志页视图层内调整滚动判定与跳转交互：

- 首次进入不自动滚到底部
- 底部跟随阈值改成按 3 条日志高度计算
- 增加日志区右下角单个浮动按钮，根据当前位置在“回顶部”和“去底部”之间切换

## 设计要点

### 1. 首次进入不自动滚动

页面首次挂载以及历史日志加载完成后，不主动调用 `scrollIntoView()` 或 `scrollTo()`。

这意味着：

- 若历史日志已经超过可视区，用户初次进入看到的是顶部，不会被强制拉到底部
- 若当前日志量不足以产生滚动，页面天然处于“底部附近”，后续新日志可继续自动跟随

### 2. auto-follow 只在用户仍接近底部时生效

自动跟随的语义保持为：

> 只有当用户仍位于底部附近时，新增日志才允许推动视图继续向下。

一旦用户主动上翻离开底部缓冲区，`autoFollow` 必须立即关闭；当用户重新滚回底部缓冲区，`autoFollow` 再恢复开启。

### 3. 底部缓冲区改为 3 条日志高度

新增日志滚动阈值计算逻辑，依据单条日志项的已渲染高度计算：

- `threshold = rowHeight * 3`

考虑到日志项可能因消息换行而异常偏高，阈值需要做上下限夹取，避免单条超高日志把缓冲区放得过大：

- 最小值：`72px`
- 最大值：`240px`

如果无法读取有效行高，则回退到保守默认值，例如 `96px`。

### 4. 浮动按钮使用单按钮切换模式

浮动按钮固定在日志滚动卡片右下角，仅在容器可滚动时显示。

按钮状态规则：

- 当前位于底部附近：显示“回顶部”
- 当前不在底部附近：显示“去底部”

按钮点击规则：

- 点“去底部”：平滑滚动到底部，并将 `autoFollow` 设为开启
- 点“回顶部”：平滑滚动到顶部，并将 `autoFollow` 设为关闭

### 5. 保留顶部现有入口

顶部现有“回到底部”按钮先保留，不在本轮清理。

原因：

- 桌面端已有操作路径不变
- 浮动按钮主要补足长列表区域内的快速跳转
- 可避免这次把“交互体验修复”扩大成 UI 收口改造

## 状态设计

日志页需要明确以下滚动相关状态：

- `autoFollow`
  - 当前是否允许新增日志继续自动跟随到底部
- `hasScrollableOverflow`
  - 日志容器当前是否存在可滚动溢出
- `scrollContainerRef`
  - 指向日志滚动区，用于读取滚动位置和执行顶部/底部跳转

浮动按钮显示模式不一定需要单独存状态，可基于当前位置即时计算：

- `isNearBottom(scrollContainer, threshold)` 为 `true`：显示“回顶部”
- 否则：显示“去底部”

## 测试策略

必须覆盖以下行为：

1. 固定 `48px` 不再作为唯一阈值来源
2. 行高为正常值时，阈值按 3 条日志高度计算
3. 行高异常偏大时，阈值会被最大值夹住
4. 用户明显上翻时，不应继续自动跟随
5. 容器未溢出时，仍可视为在底部附近

页面交互层面的最终验证关注：

- 首次进入日志页时不自动跳到底部
- 上翻后新日志到来不再把视图拉下去
- 点击浮动按钮可正确切换顶部/底部跳转

## 风险与控制

### 风险

- 如果阈值计算过大，用户轻微上翻后仍可能被继续跟随
- 如果阈值计算过小，用户接近底部时又可能过早失去自动跟随
- 如果直接依赖某条日志项高度，极端超长日志可能影响体验

### 控制

- 用阈值夹取限制异常高度影响
- 优先把阈值计算沉到纯函数，先用单测固定行为
- 页面层只做最小状态改动，避免扩大到 `useLogsStream`
