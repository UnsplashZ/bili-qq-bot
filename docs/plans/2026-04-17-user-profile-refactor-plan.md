# 2026-04-17 用户画像重构计划

## 背景

当前用户画像链路已经能工作，但存在几个会在大群长期运行中放大的问题：

1. 画像生成触发与“Bot 本轮是否回复”耦合，导致大量本应累计并更新画像的用户长期得不到刷新。
2. 画像存储模型是单一字符串，不利于后续演进、调试与兼容治理。
3. 画像生成虽然已经按 userId 过滤上下文/向量记忆，但整体链路仍缺少更明确的用户级证据与状态字段，排查困难。
4. 向量记忆的近似去重逻辑会跨用户合并相似发言，这会削弱基于 userId 的画像准确性，属于明显的相关正确性风险。
5. 现有测试覆盖偏轻，尤其缺少“独立触发”“结构化兼容注入”“跨用户污染防护”方面的保障。

## 目标

在不大改架构的前提下，做一轮偏生产化、可渐进迁移的重构：

- 将“元数据累计”和“画像生成触发”解耦。
- 让画像更新不再依赖 Bot 是否实际回复。
- 引入结构化画像模型，同时保留现有 prompt 注入所依赖的兼容摘要文本。
- 为画像记录补充最小但有用的生成状态、来源统计与轻量证据。
- 强化按用户隔离，降低大群中跨用户污染风险。
- 保持私聊排除策略不变。
- 增补最小必要测试，优先覆盖正确性风险点。

## 实施方案

### 1. 重构 userProfileService

- 对画像条目做统一归一化，兼容老数据：
  - 保留 `profile` 作为兼容摘要文本。
  - 新增结构化字段，如 `profileData`、`profileSummary`、`profileVersion`、`evidence`、`sourceStats`、`generationStatus` 等。
- 将“是否应更新”提炼为独立 eligibility 逻辑。
- 将触发入口调整为独立的调度/检查方法，允许在记录消息后立即后台检查，而不依赖 AI 回复分支。
- 生成阶段只使用目标用户自己的消息，收集：
  - AI context 中该用户的消息
  - vector memory 中该用户的消息
- 生成 prompt 改为优先请求结构化 JSON，失败时回退到文本摘要解析，避免硬依赖模型完美输出。
- 生成完成后同时写入：
  - 结构化画像
  - 兼容摘要文本
  - 轻量证据（截断后的样本）
  - 来源统计
- 保留 `maybeUpdateProfile` 兼容入口，内部转发到新逻辑，降低调用面改动风险。

### 2. 调整 messageHandler 触发时机

- 在非命令消息被清洗并入库后：
  - 继续写入 vector memory
  - 继续记录画像元数据
  - 直接异步触发画像 eligibility 检查
- 不再把画像更新绑在 “AI 已回复” 分支下。
- 保证记录元数据和触发检查按顺序执行，避免竞态下首次达到阈值却漏触发。

### 3. 提升 prompt 注入兼容性

- retrieval augment 改为使用“兼容摘要提取”逻辑，而不是直接假设 `entry.profile` 一定是唯一字段。
- 保证旧数据、纯文本新数据、结构化新数据都能继续注入 `[ACTIVE_PROFILES]`。

### 4. 修复相关跨用户污染风险

- 调整 vectorMemoryService 的近似去重策略：
  - 用户消息仅允许与“同一 userId 的同类消息”合并。
  - 避免不同用户因为说了相似短句而被错误折叠到同一记忆项。
- 这是用户画像正确性的直接前置修复，风险低、收益高。

### 5. 测试

新增或更新单测，覆盖：

- 画像条目归一化与老数据兼容读取。
- 画像 eligibility 与“独立于 Bot 回复”的触发语义。
- retrieval augment 对结构化画像/兼容摘要的注入。
- vector memory 不再跨用户错误合并。

## 风险与控制

- LLM 结构化输出不稳定：通过 JSON 解析失败回退到摘要文本，避免功能中断。
- 新字段落盘后旧逻辑读取：保留 `profile` 兼容字段，先兼容再演进。
- 触发时机提前可能带来更多生成尝试：通过既有阈值、并发锁与失败后状态记录控制。
- 大群数据量增长：本次只做轻量证据与来源统计，不引入重型索引或后台任务系统。
