# 2026-02-28 动态/Opus/CV 预览排版优化实施计划（增量改造）

## 1. 背景与目标

当前项目对以下链接类型已有较复杂分流与解析：

1. `t.bilibili.com/<id>`（动态）
2. `bilibili.com/opus/<id>`（Opus）
3. `bilibili.com/read/cv<id>`（专栏）

现有链路总体可用，但在“文章型动态（动态里挂 cv）”场景，正文质量与排版稳定性仍有问题，典型表现为：

1. 正文被 `[图片]` 占位符打断，可读性差。
2. 专栏与动态在正文区域视觉节奏不一致（分区、内边距、图文对齐）。
3. 同一内容在不同入口（`t` / `opus` / `cv`）输出效果不一致。

本计划目标：

1. 在**不推翻现有判断链路**前提下，补齐“内容来源优先级 + 轻量清洗 + 排版统一”。
2. 保证当前功能正确执行，不改变消息发送流程、API 契约与默认策略。
3. 保持最终图片总宽与现有卡片一致，不引入无关变量。

## 2. 现状链路梳理（基于当前代码）

### 2.1 入口与取数

1. 链接识别：`src/handlers/linkHandler.js`
2. 动态详情：`biliApi.getDynamicInfo()` -> `bili_server.py:get_dynamic_detail()`
3. Opus 详情：`biliApi.getOpusInfo()` -> `bili_server.py:get_opus_detail()`
4. 专栏详情：`biliApi.getArticleInfo()` -> `bili_server.py:get_article_info()`

### 2.2 渲染层

1. 动态：`src/services/imageGenerator/renderers/dynamic.js`
2. 专栏：`src/services/imageGenerator/renderers/article.js`
3. 公共样式：`src/services/imageGenerator/core/theme.js`
4. 媒体块：`src/services/imageGenerator/renderers/components/media.js`

### 2.3 已验证的数据质量差异（2026-02-28 本地含 cookie 实测）

以 `689560675879485457` 为例：

1. `dynamic.get_info()`：`desc.text` 为空，`summary.text` 长度约 `534`，含 `7` 个 `[图片]` 占位，且 `pics` 可能缺失或不全。
2. `opus.get_info()`：可拿到结构化段落（约 `144` 段，文本段 `133`，图片段 `11`），内容明显更完整。
3. 解析到 `cv17878862` 后，`get_article_info()` 可拿到更完整的 `summary/html_content`，但原文可能自带空段落（数据源特征）。

结论：文章型动态只依赖 `summary.text` 不够稳定，需要更清晰的来源优先级。

## 3. 当前问题定义

### 3.1 数据层问题

1. 文章型动态正文来源优先级不明确，常落到低质量摘要。
2. `[图片]` 占位符未经语义清洗，直接参与渲染。
3. `t`/`opus`/`cv` 三入口同源内容，输出文本完整度差异明显。

### 3.2 展示层问题

1. 专栏正文区与统计栏虽然已补分割线，但仍需与动态保持统一 token（粗细、色值、间距节奏）。
2. 专栏正文图片需严格遵循“与文本同一内容宽度、左右对齐”的统一规则。
3. 动态与专栏在正文-媒体-数据区的间距策略需收敛，避免同类内容观感漂移。

## 4. 方案选型

### 4.1 方案 A：保持现状

1. 优点：零改动、零风险。
2. 缺点：文章型动态可读性问题持续，入口一致性问题不解决。

### 4.2 方案 B：仅做样式统一，不改正文来源

1. 优点：改动面小，视觉问题可缓解。
2. 缺点：核心“内容怪异”问题仍在，尤其 `[图片]` 占位符问题。

### 4.3 方案 C：样式统一 + 来源优先级优化（推荐）

1. 优点：同时解决“内容质量 + 排版一致性”。
2. 风险：涉及动态正文决策，需严格回退与兼容策略。
3. 适配性：可在现有分流链路上增量实现，不推翻架构。

## 5. 推荐方案（方案 C）详细设计

## 5.1 统一内容决策层（仅用于预览渲染）

为动态渲染引入“正文候选源”决策，不改消息流程：

1. 普通动态：`desc.text` 优先。
2. Opus 动态：`opus.summary` 次优先（并做占位符清洗）。
3. 文章型动态（命中 `jump_url` 含 `read/cv` 或 `type=ARTICLE`）：
   - 优先使用更完整来源（`article` 或 `opus` 结构化段落）。
   - 现有摘要作为兜底，不可用时回退旧逻辑。

说明：该层仅决定“渲染文本输入”，不改变业务侧“内容类型判定”与推送行为。

## 5.2 占位符清洗规则（最小语义改动）

对正文文本执行轻量清洗：

1. 当同条内容存在真实图片数组时，移除或折叠多余 `[图片]` 占位串。
2. 保留必要换行与基本标点，不做激进重写。
3. 清洗失败时回退原文，确保不会因清洗中断渲染。

## 5.3 专栏/动态排版统一策略

在保持当前视觉基线基础上统一 token：

1. 分割线：专栏统计栏与动态 `action-bar` 使用一致边框粗细和对比度。
2. 内容内边距：专栏内容区与其他卡片统一左右留白策略，保持最终卡片总宽不变。
3. 正文图片：专栏正文图按内容区宽度自适应，至少与文本左右边界对齐。
4. 间距节奏：正文、媒体、统计栏的上下间距按统一 token 收敛，不做结构重排。

## 5.4 兼容与回退

1. 任何新增来源读取失败，立即回退当前可用链路（`desc` / `summary`）。
2. 不删除现有字段，不修改旧字段语义，只新增“决策优先级”与“清洗后文本”使用点。
3. 保持所有非文章型卡片输出与当前基本一致。

## 7. 风险评估与控制

主要风险：

1. 正文来源切换导致个别动态文本长度突增，出现截断差异。
2. 清洗策略误删有效文本（低概率）。
3. 专栏样式收敛导致局部视觉与历史截图有细微差异。

控制措施：

1. 仅在命中明确条件时切换优先来源（文章型动态优先）。
2. 清洗规则保持“可逆/可回退”，并设置保守阈值。
3. 每步修改后都用固定链接回归截图，对比视觉差异。

回滚方案：

1. 先回滚正文决策层（恢复旧优先级）。
2. 再回滚清洗规则。
3. 最后回滚样式 token 变更（保持分割线修复可独立保留）。
